# Analysis: Ollama, Modelfiles, and Multi-User Serving

## Scenario and concepts

This demonstration uses TrailMate, a practical overnight camping assistant. Its default behavior is intentionally constrained: it answers in three to five concise bullets, and for a forecast at or below 0 degrees Celsius it must recommend a sleeping bag rated for that temperature or colder, an insulated sleeping pad, and warm base layers. This gives us an observable rule to test, plus ordinary questions about tent condensation and simple arithmetic. Since this machine has Groq credentials but no local Ollama service, the actual timed experiment was run through Groq using the same default system prompt. The `Modelfile` remains the equivalent local Ollama packaging example; Groq does not load or execute that file.

A Large Language Model generates text from patterns learned during training and the prompt context it receives. By itself, it does not fetch current weather or execute a local command; it may produce useful explanations, but it cannot guarantee current or externally verified information unless such information is provided to it. In this example, TrailMate must not pretend to know live weather and can only use the forecast supplied in the question.

Ollama is a model-serving application: a client can use it through its command-line interface, its HTTP REST API, or its OpenAI-compatible API. The command line can create and run models (`ollama create`, `ollama run`); the REST API supports endpoints such as `/api/generate` and `/api/ps`; and the OpenAI-compatible endpoint `/v1/chat/completions` lets code using familiar chat-completion message structures talk to Ollama. These are different interfaces to a running model service, not different models. Ollama could not be run here because its executable is absent and `localhost:11434` refuses connections.

The `Modelfile` starts with `FROM qwen2.5:1.5b`, defines multiple `PARAMETER` defaults, and stores the TrailMate behavior in `SYSTEM`. Running `ollama create trailmate -f Modelfile` packages those defaults into a named custom model. With Ollama, a request that supplies no system message should receive the Modelfile behavior by default, while an OpenAI-compatible request can supply a different system prompt. The actual conflict test in this report used Groq, so its TrailMate default was passed as the request's system message and its override was passed as a different request's system message; neither call used the Modelfile. This demonstrates per-request prompt behavior on Groq, but does not establish Ollama's Modelfile precedence. The model file supplies defaults, not an unchangeable policy boundary, so actual responses must be inspected rather than assumed.

## Run and measurement method

`groq_demo.py` sends one non-streaming request for the cold-weather rule test, then streams the condensation question, the arithmetic question, the repeated condensation question, and the system-prompt override. Streaming TTFT is measured from request start until the first non-empty content arrives. Total time is measured through the last streamed event. Tokens per second uses Groq's reported completion-token count divided by generation wall time after TTFT; the non-streaming rate uses its completion-token count over full request time, so compare it cautiously with streaming runs. Non-streaming delivery is buffered, so TTFT is N/A for that run. Groq exposes neither Ollama `/api/ps` nor Ollama `load_duration`, and its hosting layer does not provide a per-model resident-memory indicator to this client; cold-versus-warm model residency therefore cannot be concluded from these requests.

TTFT is the initial wait before visible output, while total time includes that wait and the remaining generation. In the condensation runs, TTFT was most of the total time (0.410 of 0.532 seconds and 0.405 of 0.443 seconds), so output generation after the first text was comparatively quick. The arithmetic response was very short; its computed token rate is consequently unusually high and sensitive to timing granularity, so it should not be treated as a stable benchmark. The repeated condensation response took less total time than the first (0.443 versus 0.532 seconds), but TTFT was similar (0.405 versus 0.410 seconds), and Groq does not report whether the model was already resident. This does not prove a warm-load effect. The non-streaming cold-weather result followed the TrailMate rule, but its TTFT could not be measured because the response was buffered. The override followed the requested paragraph format and changed the persona; it also introduced an unsupported claim that the National Weather Service advises campers. This is a useful reminder that a style override does not guarantee factual grounding.

## Why a shared deployment needs a different server

Ollama is convenient for local development and small-scale use, but serving many simultaneous users creates GPU-memory and scheduling pressures. Each active request has a prompt and a growing key/value (KV) cache representing its context. Reserving large contiguous cache regions per request can waste memory through fragmentation, while requests have different context lengths and finish at different times. A server must decide how to admit, schedule, and batch these requests without starving short requests or exhausting accelerator memory.

vLLM is designed for high-throughput model serving. PagedAttention manages the KV cache in fixed-size blocks rather than requiring each request to occupy one large contiguous region; blocks can be allocated as needed and shared/managed more efficiently, reducing fragmentation and improving memory utilization. Continuous batching dynamically adds new requests to a running batch as other requests finish, rather than waiting for the whole batch to complete before admitting more work. Together, these mechanisms improve concurrency and throughput for multi-user deployments, though actual capacity still depends on the model, hardware, context sizes, and workload.

## Observations and conclusion

The Groq run shows that a behavior supplied in a system prompt can shape answers, and that a different system prompt can change the style for a single request. It does not show that a Modelfile was loaded: Groq does not support Ollama's Modelfile format or its CLI/REST residency controls. Ollama remains suitable for local development and single-user experiments where a custom model profile and local process control are useful. For a deployment shared by many users, request concurrency creates GPU-memory and scheduling pressures. vLLM's PagedAttention manages KV-cache memory in blocks to reduce fragmentation and improve utilization, while continuous batching admits new requests as other requests finish instead of waiting for an entire fixed batch. These techniques make vLLM a more suitable serving layer for high-concurrency inference. An Ollama-specific timing and residency comparison still requires an Ollama-enabled machine; Groq cannot provide the missing local-residency measurements.
